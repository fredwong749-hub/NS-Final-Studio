# AI 短剧自动制作系统：深度调研与最终设计方案

> 目标交付文件：`script play lib/design md file.md`
>
> 本方案不包含产品代码。审阅通过后，仅需将本文写入目标文件，不修改 folder 中现有三份资料。

## 0. 执行摘要

这个系统不应做成“把长提示词批量发给模型”的工具，而应做成四层产品：

1. **资产编译器**：把故事、分镜、每集图片提示词解析为结构化镜头，并把镜头中的人物绑定到已经确认的人物、造型、衣服、身材、发型、美甲和高跟鞋参考资产。
2. **确定性生产工作流**：人物资产确认并锁定后，自动完成首帧生成、候选选优、图生视频、连续性质检、有限重试、配音、剪辑和归档。
3. **统一模型适配层**：Qwen Image 2.1 Turbo 负责定稿首帧；MiniMax H3 本地默认采用 `ComfyUI + ComfyUI-Omnichar + ComfyUI-MiniMaxH3Mod`，云端 H3 仅作 2K 和对照路径。不同接口的参数不能混用。
4. **异构 GPU 集群**：图片任务以单卡 worker 横向扩展；本地 H3 以 ComfyUI worker 组成推理单元，实际卡数与拓扑按 POC 确定；后期与质检独立调度。云端模型任务则受账号并发和限流约束，本地 GPU 无法加速云端推理。

**推荐主流程：资产只确认一次，之后全自动；任何镜头只能“通过质检后导出”或“明确进入异常队列”，不能用不合格镜头静默凑成片。**

## 1. 需求边界与最终使用方式

### 1.1 用户每轮提供

- 故事剧本及集、场、镜结构。
- 每镜画面、动作、运镜、声音、对白、独白、时长等信息。
- 每集或每镜图片提示词；如图生视频脚本已经写好，也一并导入。
- 项目级画幅、视觉风格、时长、成本与质量策略。

系统默认**保留原始创作内容，不擅自重写剧本**。Agent 的工作是识别、绑定、校验、编译和执行，不是替用户重新创作。

### 1.2 用户只做一个强制确认

确认“人物资产包”：每个角色在各剧情阶段的 face、body、hair、makeup、nails、outfit、shoes、配饰、音色及参考图。

确认后形成不可变的 `asset_pack_version`。后续修改必须生成新版本，并明确影响哪些集、场、镜；已经开始生产的镜头仍绑定旧版本，避免全局改动把在途任务污染。

### 1.3 系统自动交付

- 每镜定稿首帧及候选、参考图顺序、生成参数和质检报告。
- 每镜视频及失败重试记录。
- 每集成片、字幕、音轨、时间轴和连续性台账。
- 无法自动修复的镜头异常清单；其他镜头继续生产，不整集等待。

- `script play lib/为他而骚（3提示词纠正器） v2.md:149` 已识别镜面、暗场、复杂饰品、多场景跟拍等高风险镜头，适合作为首轮 POC 测试集。

### 2.2 需要修正的关键点

| 当前资料做法 | 问题 | 本方案修正 |
|---|---|---|
| 以少量角色基准图覆盖所有造型 | 无法独立管理衣服、鞋、美甲、发型、身材及剧情变化 | 角色身份、角色造型、单品、参考图、镜头出场分别建模并版本化 |
| 通过完整提示词前缀“锁死人物” | 文本不能提供稳定身份，且长提示词会引入相互冲突的信息 | 以精选参考图、定稿首帧、镜头级可见属性和自动质检共同保证 |
| 禁止跨集并行以防风格漂移 | 串行不是一致性的根因，会浪费集群产能 | 用同一资产版本、提示词编译器版本和生成配方保证一致性；无依赖镜头并行 |
| 假设 H3 可能支持首尾帧 | 现已明确支持 | 对动作明确的镜头启用首尾帧；先做首帧/尾帧兼容性 POC |
| 云端首尾帧与人物参考可叠加 | MiniMax 云端 V2 明确两种模式互斥 | 云端先把人物参考烘焙进首帧，再走 FL2VA；本地混合模式单独验证 |
| `motion_strength`、通用 `negative`、视频 `seed` 可直接用于 H3 云端 | 官方 V2 未公布这些通用参数 | 云端只使用文档字段；本地 ComfyUI 或其他后端的参数分别按各自实现验证，不能混用 |
| Qwen 的垫图权重和 `negative_prompt` 可照搬 | 百炼 Turbo 无垫图权重字段，2.1 的 `negative_prompt` 不作为可用负向分支参数 | 以参考图顺序和角色化文本约束；禁止描述改写进正向提示；参数按适配器白名单 |
| 固定“人脸相似度 >85%”“装饰存活 98%”即可自动验收 | 不同人脸识别模型分数不可比，且被遮挡资产不应要求每帧可见 | 用项目金标集校准阈值；按“应在场、实际可见、剧情状态”分别检查 |
| 每 10 秒抽 1 帧即可验证连续性 | 会漏掉短时变脸、闪烁和中间动作崩坏 | 首帧、尾帧、均匀抽帧、异常帧触发加密抽样和人物跟踪 |
| 6×10 秒并加 0.3 秒交叉溶解仍为 60 秒 | 5 次重叠会减少约 1.5 秒 | 用时间轴时长模型统一计算；需要溶解时预留手柄或采用不重叠转场 |
| 文本声称独白可在 10 秒念完即视为通过 | 多部文字实际时长需由音色和语速决定 | 渲染前生成 TTS 预演，按真实音频时长校验；允许独白跨镜，口型对白不得超时 |
| 敏感内容通过“降级替换表”继续提交 | 云端审核可能拒绝，且不能用系统绕过安全机制 | 做合规预检、明示阻断、人工改写和发行渠道审查，不自动规避审核 |

此外，folder 中的部分成人及高敏感内容可能触发模型和发行平台审核。MiniMax H3 官方模型卡明确说明，涉嫌色情、违法或侵权的文本、图片、视频及增强提示词可能被阻断。因此，量产前必须先确认内容合规与目标渠道，不应把“能生成”误认为“能发布”。

## 3. 小云雀调研：真正值得复用的产品逻辑

### 3.1 官方链路

小云雀 Web 官方手册给出的短剧流程是：上传/生成剧本、确认全局设定、拆解全局角色、拆解全局场景、分集故事板编辑、合成导出。其 Agent 会提取角色在不同时空的妆造并映射到集号，故事板支持 `@` 引用角色和场景、批量生成多集和多分镜、截取上一镜尾帧作为下一镜参考。[小云雀 Web 产品手册](https://www.xiaoyunque.com/tutorials/web-manual)

官方资产画布进一步说明：

- 画布节点不是普通图片便签，而是角色、场景、道具、素材等可复用资产。
- 节点连线代表引用上下文；角色/场景节点可作为后续生成参考。
- 角色支持子形象、三视图、打光、镜头控制和音色参考。
- 资产可同步到故事板，但“一处更新全链路生效”在本系统里必须增加版本和作用域，不能无条件回写历史镜头。[短剧 Agent 画布手册](https://www.xiaoyunque.com/tutorials/short-drama-agent-canvas)

智能预演的价值是把整组镜头先统一规划为关键分镜图，确认后再生成视频，减少逐镜抽卡。官方建议先确认剧本和每幕分镜，再做预演。[智能预演指南](https://www.xiaoyunque.com/tutorials/short-drama-agent-smart-preview)

3D 导演台用于多人站位、空间关系、姿势、动作轨迹、机位和时间轴预演，其输出还要与角色图、场景图和文本一起进入生成链路；它不是直接取代人物资产的 3D 成片器。[3D 导演台手册](https://www.xiaoyunque.com/tutorials/short-drama-agent-3d-director)

### 3.2 本系统应该借鉴与不应该照搬的部分

**第一版就借鉴：**

- 全局角色/场景资产库及剧情阶段子形象。
- 故事板中的 `@资产` 引用和镜头级参考素材。
- 先整组关键帧预演、再视频生成的成本控制思路。
- 单镜返工、批量任务、中间过程保留、素材来源可追溯。

**增加自己的差异化：**

- 衣服、身材、美甲、高跟鞋、face 等插槽级资产管理，而非只有一个角色主图。
- 参考图按镜头可见内容动态选择，避免每镜把所有图片都塞给模型。
- 自动质检、自动选优、自动重试和 GPU 集群调度。
- 不可变资产快照、完整生成血缘、成本预算和异常队列。

**暂缓：**

- 完整 3D 导演台不是 MVP。先把 2D 资产画布、故事板和参考图生产跑通；多人复杂调度、同场景反打和复杂运镜再增加 3D 预演。
- 不做泛化“聊天生成一切”的首页。你的入口已经非常明确：剧本 + 分镜 + 每集图片提示词 + 已确认人物资产。

近期公开报道显示小云雀已并入即梦体系但保留独立入口，说明“短剧 Agent 工作流 + 通用模型与画布能力”正在整合；本系统采用模型适配层，避免依赖某一家的产品包装。[相关报道](https://www.ithome.com/1/017/480.htm)

## 4. 模型能力核查与正确用法

### 4.1 Qwen Image 2.1 Turbo

官方确认该模型为 7B 视觉生成架构，Turbo 使用 8 步采样，支持文生图、图生图和多参考编辑；官方仓库与百炼文档均说明 2.1 系列最多可输入 10 张参考图。[Qwen 官方仓库](https://github.com/QwenLM/Qwen-Image-2.1) [百炼 API 参考](https://help.aliyun.com/zh/model-studio/qwen-image-generation-and-editing-api-reference)

云端百炼关键点：

- 模型 ID 为 `qwen-image-2.1-turbo`，每张 0.1 元，文档标注 120 RPM；实际以账号和地域为准。[模型与价格](https://help.aliyun.com/zh/model-studio/qwen-image-2-1-turbo)
- 支持 1–10 张输入图、1–6 张输出图、seed、同步/异步调用；结果 URL 仅短期有效，必须立即转存自己的对象存储。
- `prompt_extend` 默认开启。对于用户已锁定的提示词，生产模式应关闭自动改写，或保存改写前后文本并纳入版本；不能让模型悄悄改变创作约束。
- 不应虚构“垫图权重 0.72”等接口参数。Turbo 使用固定 8 步调度与 CFG=1，不能照搬普通模型的 negative/CFG 调参经验。[Turbo 模型卡](https://huggingface.co/Qwen/Qwen-Image-2.1-Turbo)
- 官方自托管推荐 9:16 的 1536×2752；百炼还需遵守其像素面积限制。可先用 1152×2048 作为 9:16 云端候选规格，再 POC 比较细节和成本。

**授权红线：**自托管权重使用 Qwen Research License，只允许研究/评估，商业使用需另行取得授权；不能把“可下载”理解为“可免费商业自架”。托管 API 则按服务平台条款评估。[Qwen Research License](https://huggingface.co/Qwen/Qwen-Image-2.1-Turbo/raw/main/LICENSE)

### 4.2 MiniMax H3 云端

MiniMax V2 官方文档确认：

- 标准 `MiniMax-H3` 支持 4–15 秒、768P/2K，文生视频、首帧、尾帧、首尾帧、多模态参考。
- 图片最多为首帧 1 张、尾帧 1 张；参考图最多 9 张，并可使用参考视频和音频。
- **云端图生视频与多模态参考互斥**：一次请求不能同时用 `first_frame/last_frame` 和 `reference_image/reference_video/reference_audio`。
- 图生视频比例跟随输入图，因此必须在 Qwen 阶段生成正确 9:16 首帧，不能依赖 H3 再强制改比例。
- 支持任务回调和查询，采用异步生产；未公布 folder 中所写的通用 `motion_strength`、视频 seed、通用 negative 字段。[MiniMax V2 创建任务](https://platform.minimax.cn/docs/api-reference/video-generation-v2-create)

官方提示词指南要求把视频描述组织为：首帧/首尾帧对齐说明、`integrated_multimodal_description`、`overall_soundscape`、`non_diegetic_music`；对白使用稳定说话人 ID 和 `<d>` 结构，独白要明确为画外音且人物嘴唇保持闭合。运镜应写“运动类型 + 幅度 + 速度”，而不是堆叠抽象标签。[H3 基础提示词指南](https://raw.githubusercontent.com/MiniMax-AI/MiniMax-H3/main/skills/h3-prompt-writing/references/base-en.txt)

### 4.3 MiniMax H3 本地 GPU：指定 ComfyUI 技术栈

H3-Base 已开放 FL2VA 与 Ref2VA 两种 checkpoint。基础模型可生成 768P、24fps、32kHz 立体声，完整系统还包含未开放的 Context-IR 和 2K 再生成模块。[H3 官方模型卡](https://huggingface.co/MiniMaxAI/MiniMax-H3)

本项目本地默认栈明确为：

| 组件 | 在本系统中的职责 | 不能误解为 |
|---|---|---|
| ComfyUI 原生 MiniMax H3 | 执行 FL2VA/Ref2VA 工作流和视频生成 | 与官方完整 2K 托管工作流完全等价 |
| [ComfyUI-Omnichar](https://github.com/omnichar/ComfyUI-Omnichar) | 读取/生成 `.char`，管理有序 face、body、wardrobe 参考，传递可选 LoRA 和声音参考 | 覆盖所有美甲、鞋、发型等细粒度资产，或保证身份一致 |
| [ComfyUI-MiniMaxH3Mod](https://github.com/Luisacaotica/ComfyUI-MiniMaxH3Mod) | 把图片、视频、音频参考提取为可复用 RefMod `.safetensors`，缓存 VAE latent，组合并注入 H3 | 人物训练、DreamBooth、语义解耦、精确动作控制或可靠声音克隆 |

具体约束：

- `.char` 当前提供 face/body/cloths 各三个槽位并保持参考顺序。内部资产模型仍是其超集；美甲、鞋、发型、妆面等先在自己的资产库中管理，再导出为 `.char`、有序图片或独立 RefMod，不为迁就文件格式丢掉信息。
- RefMod 的 `Full Reference / encode` 保存较多细节，作为身份保真基线；`Compressed Reference / training` 只是池化与 MSE 压缩优化，不训练 H3 权重，也不学习“应该保留哪个属性”。压缩可能丢失人脸、材质和动作信息。
- 每个角色使用独立 `.char` 和 RefMod 文件，避免身份、衣服、背景、构图相互串扰。RefMod 的 token 数、裁切、参考顺序、latent 形状、源文件哈希和节点版本都进入资产生成血缘。
- 默认定稿首帧走 FL2VA；只有确实需要人物/动作参考的镜头才走 Ref2VA + RefMod。原生 Ref2VA 与 RefMod 预处理并不等价，必须做同参考、同 prompt、同 seed 对照。
- Omnichar 的声音输入只能期望相似音色；MiniMaxH3Mod 文档更明确表示当前 speaker identity transfer 不可靠。因此正式跨集配音仍用固定 TTS，原生/RefMod 声音仅进入实验队列。
- MiniMaxH3Mod 标注为 under construction，节点名称和输入可能变化。生产环境必须固定 ComfyUI、两个自定义节点及模型文件的版本/commit，保存可重放 workflow 和金标回归结果，禁止自动跟随 main 更新。
- SGLang 的 4 卡拓扑和性能数据只作为硬件参考，不能直接当成 ComfyUI worker 的参数或实测结果；ComfyUI 的显存、并行和吞吐必须独立压测。

许可还需分别审查：Omnichar SDK 为 Apache-2.0，其余部分为 GPL-3.0-or-later；MiniMaxH3Mod 为 MIT；H3 权重仍有自己的社区许可和地域条款，不能用节点许可替代模型许可。

### 4.4 推荐模型路由

| 任务 | 首选路径 | 备选路径 |
|---|---|---|
| 人物资产与定稿首帧 | 百炼 Qwen 2.1 Turbo，快速合规上线 | 获商用授权后自建单卡 Qwen worker |
| 角色资产交换 | 内部资产快照导出 `.char` + 有序参考图 | 独立 Full Reference RefMod 保存可复用 latent |
| 日常动作预演 | 本地 ComfyUI H3-Base，固定工作流 | H3 Lite/Highspeed 仅作低成本对照，不假定输出相同 |
| 最终视频 | 本地 ComfyUI H3 FL2VA 768P，定稿首帧/必要尾帧 | 云端 H3 标准版 768P/2K，或本地 Ref2VA POC 通过后的参考路径 |
| 高控制动作 | 定稿首帧 + 尾帧的 FL2VA | Ref2VA + Full Reference RefMod，必须与原生参考路径对照 |
| 系列一致配音 | 固定音色 TTS/授权声音资产，后期混音 | Omnichar/H3 声音参考仅实验，不承诺音色复制 |

## 5. 总体系统架构

### 5.1 控制面与生产面分离

**创作与控制面**

- 项目/剧集/场景/镜头数据。
- 人物资产库、版本、参考图、可见属性和连续性状态。
- 提示词编译器、资产绑定、成本预估、审批与异常处理。
- PostgreSQL 保存真相；对象存储保存原始文件和生成物；Redis 只用于缓存和短期状态，不能当唯一真相源。

**工作流面**

- Temporal 管理长任务、等待资产确认、并行分发、重试、超时、崩溃恢复和人工异常。
- Agent 只提出结构化绑定与修改建议；真正的状态迁移、费用扣除、重试和导出由确定性工作流执行。[Temporal Durable AI](https://docs.temporal.io/ai)

**生成面**

- Qwen 云适配器、本地 Qwen worker。
- 本地 headless ComfyUI worker：加载固定版本的 Omnichar、MiniMaxH3Mod、H3 FL2VA/Ref2VA 和已审批 workflow。
- `.char` 与 RefMod 构建服务：只从已批准资产快照生成，产物带内容哈希，禁止 worker 自行选择其他角色文件。
- H3 云适配器作为可选 2K/对照路径；质检 worker、固定 TTS worker、FFmpeg 后期 worker 独立运行。

**集群面**

- 小规模先用一台 GPU 主机和显式资源锁验证 ComfyUI 的真实显存与并发，不预设每张卡都能独立跑 H3。
- 多节点后使用 Kubernetes + Kueue，按 POC 确定的 ComfyUI 资源形状成组分配 GPU，避免不同任务争抢同一模型单元。[Kueue All-or-Nothing Scheduling](https://kueue.sigs.k8s.io/docs/concepts/all_or_nothing/)

### 5.2 核心原则

- **数据库而非 Agent 持有真相；`.char`、RefMod 和 ComfyUI workflow 都是导出物，不是另一个可随意修改的真相源。**
- **原始剧本、编译提示词、实际 API/ComfyUI 请求三者分别保存。**
- **资产生成物不可变；每个结果都能追溯到资产版本、模型版本、参考图哈希、节点版本和参数。**
- **无依赖镜头并行；有明确首尾帧依赖的镜头才串行。**
- **外部 API 采用幂等键、provider task ID 和状态对账，崩溃后先查询再决定是否重新提交，避免重复扣费。**

## 6. 人物资产系统：本产品的核心

### 6.1 数据层级

| 层级 | 作用 | 示例字段 |
|---|---|---|
| Character | 跨集不变的身份 | 角色 ID、姓名、基础年龄、身份说明、权利与授权信息 |
| CharacterLook | 某剧情阶段的完整形象 | 生效集/场、年龄阶段、妆造名称、父角色、版本 |
| AssetItem | 可复用单品或特征 | face、body、hair、makeup、nails、top、bottom、dress、shoes、accessory |
| ReferenceAsset | 每个参考文件及其语义 | 文件哈希、视角、部位、参考职责、主色、材质、裁切、质量、来源 |
| OutfitSet | 有层次和兼容关系的服装组合 | 单品版本、穿着顺序、必备/可选、互斥规则 |
| ShotAppearance | 某镜实际出现的角色造型 | 角色造型版本、单品覆盖、位置、表情、可见部位、状态 |
| SceneAsset / PropAsset | 场景与道具连续性 | 场景版本、机位、时间/光线、道具所有者与位置 |
| ContinuityState | 剧情状态变化 | 获得、穿上、卸下、损坏、遮挡、恢复、永久/可逆、起止时间 |

`face` 和 `body` 是身份/形态参考，不与普通衣服混为一类；发型、妆面、美甲、鞋子可以有独立版本。衣服必须是“套装 + 单品 + 层次”，否则无法处理外套穿脱、鞋是否入镜、同衣不同场景等问题。

### 6.2 每类参考图最低要求

| 插槽 | 建议参考组 | 质量管理 |
|---|---|---|
| Face | 正面、左右 45°、左右侧面、中性光近景 | 无重滤镜、五官清晰、统一身份、保留原始图 |
| Body | 正/侧/背全身、自然站姿、统一光照 | 用于比例和轮廓，不用单张夸张姿势代替身体设定 |
| Hair | 正面发际线、侧面、背面、发色细节 | 长度、刘海、发色、发量分开标注 |
| Makeup | 素颜底、目标妆面近景、唇/眼局部 | 区分身份特征与可改变妆面 |
| Nails | 双手正面上指甲、左右手近景 | 甲形、长度、主色、图案、左右差异 |
| Shoes | 双鞋侧面、左右鞋外侧、正/背、上脚全身 | 鞋型、跟高视觉、开口、材质、颜色；不要只存文字“12cm” |
| Outfit | 平铺正/背、材质细节、人物上身正/侧/背 | 单品与套装关联，记录穿着顺序和遮挡关系 |
| Scene | 全景、中景、反打、必要机位、光线版本 | 尽量无人物，固定空间锚点 |

### 6.3 不直接把全部参考图塞给模型

Qwen 虽支持最多 10 张参考图，但“允许 10 张”不等于“10 张效果最好”。系统应有一个 Reference Planner：

1. 先判断镜头景别和可见部位。
2. 面部特写优先 face + hair/makeup；全身优先完整上身造型 + body + outfit；手部特写优先 nails + 手部/袖口；足部优先 shoes + 下装关系。
3. 双人镜分别为两人选择身份参考，并增加站位/构图参考；若发生身份串扰，减少无关单品参考或先制作双人定稿构图。
4. 参考图按固定顺序传入，文本明确“图 1 提供身份、图 2 提供套装、图 3 提供场景”，禁止职责漂移。
5. 默认从 3–6 张精选参考开始，POC 比较 2/4/6/10 张的身份保持、单品保真、构图和成本。
6. 对每个 CharacterLook 预生成“完整上身参考组”，减少每镜同时携带大量单品图的需要。

### 6.4 资产确认包

用户确认的不只是单张角色头像，而是一组可生产资产：

- 角色身份卡与各阶段 CharacterLook。
- 每个 Look 的正/侧/背完整形象。
- 服装、美甲、鞋、头发、妆面等单品参考组。
- 人脸近景、半身、全身、手部、足部、双人、同场景反打的测试图。
- 每集默认 Look 映射和镜头级例外。
- 未解决项清单。缺图、冲突、低置信绑定必须在锁定前处理。

锁定后由系统确定性导出三类生产物：

1. **Omnichar `.char`**：写入角色描述及有序 face/body/wardrobe 参考；超出其槽位的美甲、鞋等仍保留在内部资产快照中。
2. **Full Reference RefMod 基线包**：按角色、造型或明确参考职责分别构建，保存源哈希、VAE 版本、latent 形状和 token 数；Compressed 版本只能在对照通过后启用。
3. **镜头绑定清单**：每镜使用哪个 `.char`、哪些 RefMod、哪些首尾帧、参考顺序及职责，全部固定，不让 ComfyUI 在渲染时从文件夹自由挑选。

任何源资产变化都会产生新的 `.char`/RefMod 版本，旧缓存不得靠同名文件隐式覆盖后继续用于已锁定镜头。

### 6.5 连续性不是“每帧所有东西都在”

每个属性分成三种状态：

- `present`：剧情上存在，即使被衣服或取景遮挡。
- `visible_required`：该镜必须可见并可质检。
- `state`：穿上、卸下、持有、位置、损坏、修复等剧情状态。

质检只强制检查 `visible_required`，同时用连续性台账防止剧情上不可能的出现或消失。这能避免把“被遮住的鞋/美甲/配饰”误判为丢失。

## 7. 创作页面设计

建议一个项目工作台，顶部始终显示项目、集号、资产版本、画幅、质量档、预算和“资产确认并锁定 / 开始全自动生产”主按钮。

### 7.1 左侧：剧集与问题导航

- 集、场、镜树形结构及完成状态。
- 按缺资产、连续性冲突、生成中、质检失败、可导出筛选。
- 每镜显示角色头像缩略图和实际绑定 Look，便于快速发现错绑。

### 7.2 中央工作区一：剧本与分镜

表格字段包括：原始剧情、画面提示词、motion、camera、sound、dialogue、voiceover、duration、角色/场景/道具、可见资产、参考图、当前生成物。

- 支持粘贴文本和导入现有 Markdown。
- 原文保持只读快照，结构化字段可编辑；每次修改形成版本。
- `@` 引用资产；提示词中可以保留自然语言，但资产必须落为真实 ID，而非仅匹配名字。
- 允许设定“本集默认 Look”和“本镜覆盖”，优先级为：镜头显式设置 > 集显式设置 > 连续性继承 > 项目默认。

### 7.3 中央工作区二：资产画布

- Character 为根节点，CharacterLook 为子节点，各插槽连接 face/body/hair/nails/shoes/outfit 等资产。
- 支持拖拽上传、批量上传、自动裁切建议、视角/部位标签、参考职责标签和质量检查。
- 节点显示版本、使用范围、被多少镜头引用、是否已锁定。
- 支持“生成上身测试组”和并排比较，但只有用户能把版本标记为 Approved。

### 7.4 中央工作区三：镜头画布 / 故事板

每张镜头卡显示：

- 定稿首帧和候选图。
- 本镜实际使用的有序参考图及职责。
- 编译后的图片/视频提示词。
- 视频、QC 项、失败原因、重试次数和成本。
- 单镜、单集、全部自动生产入口；全自动模式下无需逐镜点击。

### 7.5 右侧：检查器与生产状态

- 当前镜头或资产的详细属性、版本差异和引用影响。
- GPU 单元、云任务、队列、预计剩余时间、实际费用。
- 异常队列提供“换候选、修资产、改镜头、跳过但阻止成集导出”等明确动作。

## 8. 资产确认后的全自动生产 DAG

1. **导入与结构化**：保留原文，生成 Episode/Scene/Shot 和字段完整度报告。
2. **实体识别与绑定**：识别角色、造型、衣服、鞋、美甲、场景、道具和状态变化，给出证据片段与置信度。
3. **资产预检**：检查缺图、冲突、参考质量、剧情状态、可见性、版权和敏感内容。
4. **资产锁定**：生成不可变资产快照和镜头生产清单。
5. **运行时资产编译**：从锁定快照导出 `.char`、Full Reference RefMod 和 ComfyUI workflow；核对内容哈希、参考顺序、latent token 预算及节点版本，不再读取未审批目录。
6. **TTS 与时间轴预检**：提前计算独白/对白真实时长、镜头时长、转场重叠和全集目标时长。
7. **首帧候选生成**：每镜默认 2 张，按项目策略可调整；保存完整请求和结果。
8. **图片 QC 与选优**：硬门槛剔除，再按身份、造型、构图、缺陷和提示词符合度排序。
9. **视频生成**：本地 ComfyUI 以定稿首帧/必要尾帧走 FL2VA；只有通过参考路径 POC 的镜头才使用 Ref2VA + RefMod，并保存实际 reference map。
10. **视频 QC**：身份漂移、动作、画面缺陷、资产可见性、时长、比例、音频检查；RefMod 结果还要与同设置 Full/无 RefMod 基线比较。
11. **有限自动修复**：按失败类型选择换候选、改变 seed、精简非必要描述、调整参考组或首尾帧，不擅自改剧情，也不盲目提高 RefMod 强度/复制数。
12. **后期装配**：固定音色 TTS、环境/音效、字幕、转场、画幅和编码。
13. **全集 QC 与归档**：通过项自动导出；未通过项明确阻断对应成集，并保留其他镜头的已完成成果。

### 8.1 重试分类

- 限流、网络、5xx、超时：指数退避；先对账 provider task，避免重复创建。
- 图片身份/造型失败：先换备选候选，再调整参考组合，再换 seed。
- 视频中途变脸/动作失败：优先首尾帧、减少复合动作、拆分跨场景镜头；保持用户必要剧情不变。
- 审核拒绝：不自动改写绕过，进入合规异常。
- 同一镜达到重试或费用上限：标记 Blocked；同集其他镜头继续。
- 同类失败跨镜头集中出现：熔断对应模型/配方，回到 POC 配方页面，而不是无限烧 GPU。

## 9. 提示词编译器

### 9.1 Qwen 图片提示词

按以下职责编译，而不是无脑拼接全部 DNA：

1. 本镜构图和剧情目标。
2. 每个角色的身份和当前 Look。
3. 只与本镜可见部位相关的单品细节和必要永久特征。
4. 场景、光线、镜头、风格。
5. 参考图顺序及每张图的职责。
6. 必须保持的关系和明确禁止项，以正向提示文本表达；不虚构 Turbo negative 参数。

保留 `raw_prompt`、`compiled_prompt`、`provider_prompt` 和自动改写结果。生产锁定模式默认关闭 prompt 自动扩展；研究模式可单独比较。

### 9.2 H3 视频提示词与 ComfyUI 请求

- I2VA 首行说明首帧在 0.00 秒被完整引用。
- FL2VA 明确首帧与尾帧各自对齐时间和连续变化路径。
- 主体按时间顺序描述可见动作、表情、运镜、场景变化和必要声音。
- 运镜使用“类型 + 幅度 + 速度”；避免一个镜头中无意叠加多种运镜。
- 说话人 ID 全镜稳定；原对白逐字保留。
- 画外音明确 lips closed；跨镜台词标注连续关系。
- 分别生成整合画面描述、环境/动作声和观众侧音乐三段。
- 不随意增加剧本没有的新动作、新人物或新道具。
- 使用 Omnichar/RefMod 时，提示词中的 `<Picture N>`、`<Video N>`、`<Audio N>` 必须来自实际 reference map，不能靠文件名或角色名自动触发。
- 生产基线采用原生文本编码 + Apply RefMod；实验性的 H3 RefMod Text Encode 只有在 POC 通过后启用，且同一 bundle 不得再被 Apply 或 Bridge 重复注入。
- 每次执行保存 workflow 版本、`.char`/RefMod 哈希、reference map、VAE 版本和完整参数；节点升级后先用固定金标 workflow 回归，不能直接放量。

## 10. GPU 集群设计

### 10.1 不同任务使用不同资源形状

| 资源池 | 推荐单元 | 调度方式 | 说明 |
|---|---|---|---|
| Qwen 图片池 | 1 张 80GB 级 GPU / worker 起步 POC | 多 worker 数据并行 | 批量图片重在吞吐，不为用满多卡而做低效率模型并行 |
| ComfyUI H3 FL2VA 池 | 以 4×H100/H200 节点做首轮基准硬件单元，实际使用拓扑由 ComfyUI POC 决定 | 独立 worker、整组资源预留 | 不把 SGLang 的 TP/Ulysses 参数套到 ComfyUI；未利用的卡分给其他 worker，不能空耗 |
| ComfyUI H3 Ref2VA 池 | 独立 H3 服务和固定参考 workflow | 与 FL2VA 分开 | 两种 checkpoint 与参考工作流分开管理 |
| RefMod 构建池 | VAE/CPU 预处理 worker，按实测分配 | 与视频采样错峰 | 提取参考不需要运行完整 DiT，但大量 VAE 解码与压缩仍有内存/时间成本 |
| 质检池 | 独立 GPU worker | 按人脸/VLM/视频任务排队 | 避免质检抢占正在生成的 H3 显存 |
| 后期池 | CPU 为主，可选 NVENC | FFmpeg 任务并行 | 转码、拼接、字幕、响度处理不必占用 H3 推理卡 |

vLLM 的 Qwen 2.1 测试显示，单 H200 上 BF16 1024×1024 峰值约 36.9GB；4 卡并行单图延迟改善并非线性，图片批量生产更适合单卡多 worker。2K、参考图数量和 Turbo 的实际显存/速度仍需用自己的镜头 POC。[vLLM Qwen 2.1 recipe](https://github.com/vllm-project/vllm-omni/blob/main/recipes/Qwen/Qwen-Image-2.1.md)

SGLang 的 H3 数据可用于估算硬件量级，但不再作为本项目的执行配置。ComfyUI 必须分别测量：模型加载、首任务冷启动、5/10/15 秒、9:16、FL2VA/Ref2VA、Full RefMod 数量与 token 数、峰值显存、主机 RAM、吞吐和失败恢复。

### 10.2 调度层次

- Temporal 决定“哪个镜头下一步做什么”，负责业务状态和恢复。
- Kueue 决定“任务何时获得哪几张 GPU”，负责配额、优先级、成组调度和拓扑。
- Headless ComfyUI 只接收带版本和哈希的 workflow，返回 prompt/task ID、执行状态和产物；不能在节点里隐式选择未审批资产。
- SGLang/vLLM 只作为性能参照或备选推理后端；本方案的默认 H3 执行后端是 ComfyUI。
- 云 API 适配器有独立并发令牌桶，不占用本地 H3 GPU 配额。

### 10.3 缓存与存储

- 原始上传、参考图裁切、`.char`、RefMod、候选首帧、定稿视频、QC 抽帧、TTS、字幕和最终成片全部进入 S3 兼容对象存储。
- 以资产版本 + 模型/VAE 版本 + ComfyUI/节点版本 + 提示词哈希 + 参数 + seed 做生成缓存键；不同版本不得错误复用。
- RefMod 主要省去重复参考编码，不等于生成免费：保留 token 仍参与注意力计算，加载器、Apply、Bridge 的 token 上限分别记录，禁止重复注入。
- 云端返回 URL 立即转存，不能依赖其短期有效期。
- 模型权重使用本地 NVMe/共享只读模型库，worker 预热后再接任务，避免每镜重新加载。

## 11. 自动质检与验收

### 11.1 图片 QC

硬检查：文件、尺寸、比例、人物数量、必要人物是否出现、必需可见资产、明显文字错误。

模型检查：

- 人脸检测/跟踪与已批准参考的 embedding 相似度，按角色分别判断。
- VLM 对照镜头清单检查发型、服装、美甲、鞋、场景和构图。
- 手部、肢体、融合、重复人物、非预期物件等缺陷检测。
- 分数只用于排序和告警；阈值必须用本项目人工标注的接受/拒绝样本校准，不能直接把“0.85”当跨模型真理。

### 11.2 视频 QC

- 首帧与输入图一致性、尾帧与目标帧一致性。
- 全时段人物跟踪，均匀抽帧 + 光流/嵌入异常触发加密抽帧。
- 脸部漂移、发型/服装变化、必要可见资产消失、人物数量异常。
- 黑帧、冻结、闪烁、明显变形、异常镜头切换、时长和比例。
- 运镜和动作是否符合本镜目标；复杂动作由 VLM 评分并抽样人工复核。
- 音频是否有非预期静音、削波、超长/不足；需要时对白做 ASR 文本匹配。

### 11.3 验收指标

- 资产绑定：锁定前所有必需角色和可见单品均有确定资产 ID，无未解决高置信冲突。
- 自动化完整性：每个镜头最终只能处于 Exported 或带原因的 Blocked，不允许静默跳过。
- 可恢复性：杀死一个 worker 后，已完成阶段不重复生成，外部任务不重复扣费。
- 连续性：只对镜头声明的可见项验收；永久身份特征按金标阈值通过。
- 成本：每镜、每集和项目重试次数/费用上限全部生效。
- 质量：首帧身份、视频身份、造型保持、运镜、动作和音频分别设定阈值，保留人工抽检比例。
- 时长：成片时间轴与目标时长误差不超过一帧。

## 12. 音频与后期

- 每个角色绑定固定、已授权的音色版本；跨集默认使用同一 TTS 音色，而非依赖每次 H3 原生声音自然保持一致。
- H3 可生成同步立体声，优先用于环境声和动作声的草案；是否保留进入最终混音由 QC 和项目风格决定。
- 独白可跨镜播放且人物嘴唇保持闭合；口型对白必须落在对应镜头时长内。
- 先 TTS 预演再生产视频，避免镜头完成后才发现台词念不完。
- 时间轴按帧计算。6 个 10 秒镜头若做 5 次 0.3 秒重叠溶解，结果约为 58.5 秒；若必须 60 秒，需预留额外手柄、生成较长素材再 trimming，或使用不重叠的转场。
- 输出规格建议统一 1080×1920、H.264、24fps、AAC；本地 768P 到该规格的放大只是后期放大，不等同 H3 原生 2K 再生成。

## 13. 成本模型与预算控制

以现有 60 集 × 6 镜 × 10 秒计算，共 360 镜、3600 秒成片。**本地 ComfyUI H3 是默认路径，因此云端 H3 费用只用于备选路径和云地对比，不能直接当作本地项目账单。**本地成本按“GPU 节点小时 × 实际占用时间 × 重试次数 + Qwen/TTS/存储/人工”核算，先通过 POC 得到 FL2VA/Ref2VA 和不同 RefMod token 量的真实吞吐。

云端备选路径按公开单价估算如下，未含 LLM、TTS、存储、GPU 租赁、电费和人工；价格以实际账号为准。[MiniMax 定价](https://platform.minimax.cn/docs/pricing/overview)

| 项目 | 单价 | 每轮全剧基础量 | 基础成本 |
|---|---:|---:|---:|
| H3 标准 768P | 0.50 元/秒 | 3600 秒 | 1800 元 |
| H3 标准 2K | 0.80 元/秒 | 3600 秒 | 2880 元 |
| H3 Highspeed 768P | 0.40 元/秒 | 3600 秒 | 1440 元 |
| H3 Lite 768P | 0.26 元/秒 | 3600 秒 | 936 元 |
| Qwen Turbo | 0.10 元/张 | 每镜 2 张，共 720 张 | 72 元 |
| Qwen Turbo | 0.10 元/张 | 每镜 2.5 张，共 900 张 | 90 元 |

若选择云端 2K，且平均每个通过镜头需 1.4 次生成，视频约 4032 元；加上每镜平均 2.5 张图片约 90 元，合计约 **4122 元**，仍未含其他费用。人物资产创建、`.char`/RefMod 构建和高难度镜头攻坚应单列预算。

预算控制：

- 项目启动前显示“基础量 + 预计重试 + 资产制作 + 预留”的总估算。
- 每镜设置候选数、重试次数和最大费用；每集/项目设置熔断额度。
- RefMod 保留 token、复制数、参考视频时长都进入成本预估，不能因为文件很小就忽略采样注意力成本。
- 低成本模型只用于构图/动作预演，不能把不同模型输出当成同一镜头的无损放大。
- 直接云端 2K 与“本地/云端 768P 后再生成 2K”按实际尝试次数比较；再生成后的画面仍需重新 QC。

## 14. 安全、版权与许可

- Qwen 自托管商用授权未解决前，不把本地 Qwen 权重用于商业生产。
- H3 按部署地域和用户范围审查社区许可，商业 UI 显示要求的模型标识，向用户同步使用限制和投诉处理机制。
- Omnichar 的非 SDK 部分为 GPL-3.0-or-later，SDK 为 Apache-2.0；MiniMaxH3Mod 为 MIT。集成方式、分发方式及相应义务需单独审查，节点许可不覆盖 H3/Qwen 权重许可。
- 第三方 ComfyUI 节点按固定 commit 做安全审查和依赖锁定，不自动更新；自定义节点只访问其所需模型、workflow 和资产目录。
- 上传真人脸、声音、服装参考时保存权属/授权记录；禁止未经同意仿冒真人。
- 云模型所需素材使用短时签名 URL，最小化公开范围；密钥只在服务端密钥管理中，不进入画布、日志或提示词。

- 输出保留 AIGC 标识策略、生成血缘和审计日志；不同发行平台另做规则检查。

## 16. 最终推荐默认配置

- 生产单元：镜头，而不是整集串行；成集只是后期装配与验收单元。
- 资产真相：Character → CharacterLook → Outfit/Feature → ReferenceAsset → ShotAppearance；`.char` 和 RefMod 只是版本化导出物。
- 唯一强制人工门：人物资产包锁定；其他人工只处理异常。
- 首帧：每镜 2 候选起步，动态参考组，默认关闭供应商提示词改写。
- 视频：本地 ComfyUI H3 FL2VA，优先定稿首帧，明确结尾状态用尾帧；跨场景镜头先拆镜。
- 角色与参考：Omnichar `.char` + Full Reference RefMod；Compressed、实验 Text Encode 和原生声音不默认启用。
- 模型路径：Qwen 可先用云端；H3 默认本地 `ComfyUI-Omnichar + ComfyUI-MiniMaxH3Mod`，云端 H3 作为 2K/对照备选。
- 本地集群：Qwen 单卡横向扩展，ComfyUI H3 按实测资源形状成组扩展，QC/后期独立资源池。
- 导出：只有通过 QC 的内容才能自动导出；失败可恢复、可解释、不静默。

**这套设计的关键不是复制小云雀的页面，而是建立“人物资产版本 → 镜头生产契约 → 自动工作流 → 异构 GPU 调度 → 可追溯质检”的完整闭环。**

## 17. 假设与仍需 POC 的事项

- “Image 2.1 Turbo”按 Qwen Image 2.1 Turbo 理解，而非第三方同名打包模型。
- MiniMax 本地栈明确采用用户指定的 `omnichar/ComfyUI-Omnichar` 与 `Luisacaotica/ComfyUI-MiniMaxH3Mod`，不是 MiniMax 官方节点。
- 首发为 9:16 写实短剧，现有内容规格为 6 镜×10 秒；系统数据模型允许其他集长和镜数。
- 默认用户已拥有上传人物图片、声音和其他参考素材的合法权利。
- Qwen/H3/Omnichar/MiniMaxH3Mod 的许可、商业授权、地域、内容审核与发行规则需由项目方在量产前最终确认。
- Qwen Turbo 多参考在双人、美甲、鞋和复杂服装上的最佳数量无通用答案，必须实测。
- RefMod 的最佳参考数量、压缩方式、latent/token 预算、强度与复制数没有通用最优值；提高数值不等于提高身份保真。
- Omnichar/H3 声音相似度与 MiniMaxH3Mod 当前声音迁移限制意味着固定 TTS 仍是正式方案。
- 本地 H3 Ref2VA 混合关键帧、768P 到发行规格的画面质量、与云端结果的差异均需实测。
- 所有性能、质量和费用数字均是官方资料或估算基线，不作为未经验证的产量承诺。
